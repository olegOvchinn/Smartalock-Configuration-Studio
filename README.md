# Smartalock Configuration Studio

A static HTML/CSS/JS prototype for designing, configuring and documenting Smartalock locker system deployments. No build step — open any page directly in a browser, or serve the folder with any static file server.

## Start here

Open `smartalock-templates-00.html` (**Project Registration**) — this is the site's actual starting page, and it now lives at the project **root**, not under `pages/`. It has no back-arrow at all (nothing comes before it, and rather than disabling the arrow it's removed outright). Its Contacts card includes a full-width textarea right after IT Contact — "Please provide the names and email addresses of individuals who require access to the Floorsight Administering Web Portal (1-2 people)" — saved as `project.registration.portalAccess`, autosaving on the same debounce as every other field on this page.

From there the flow is:

1. `smartalock-templates-00.html` (root) — Project Registration
2. `pages/smartalock-it-configuration-02.html` — IT Configuration & Integrations
3. `pages/pick-a-product.html` — the product picker, reached only after 00 → 02, not before

As with the Smartalock wizard, module numbers don't match click-through order here either: the actual path is **01 → 02 → 03 → 04 → 05 → 06 → 00 → `floorsense-out-of-box-policy.html`** (titled **Configuration Summary**, formerly "Out of the Box Policy" — see below). `floorsense-reservation-types-01.html` is the true entry page (its back-arrow returns to `pick-a-product.html`), then continues through Check-in Methods, Desk & User Groups, Prebooking, Business Hours, and the Optional Features hub — every setting that applies to everyone by default — and finally to Setup Path (module 00), which is no longer a decision point (see below) but a confirmation step whose Continue button leads straight to the Configuration Summary. `floorsense-default-reservation-times-07.html` onward (07–13: Default Reservation Times, Check-in Window, Auto-Release on Idle, Reservation Length, NSNP, FME, Anti Desk Hogging) are **not** part of this enforced click-through path, and — unlike every other reorder in this wizard's history — are also **no longer shown in the progress bar at all**. The progress bar was shortened from 14 segments (the old fixed 00–13 numeric list, shown identically on every page) to exactly 7, now in actual click-through order: Desk Allocation Method, Check-in Methods, Desk & User Groups, Prebooking Window, Business Hours, Optional Features, and Core Complete. All 14 numbered pages carry this same 7-segment bar — the 7 pages actually in the flow show their own segment as `current`; the 7 orphaned pages (07–13) show the identical bar with no segment marked `current`, since none of them are in the list. Those 7 pages are still fully built and functional, but per the client's direction they're meant to be reached only from the Configuration Summary when someone wants to edit a specific setting after the fact, not from the main wizard nav. Three of them (Auto-Release on Idle, NSNP, Sit-stand desks/FME) now have a `.row-edit-link` on the summary's Additional Options group linking straight in; each page's own "Save & continue" button now returns to `floorsense-out-of-box-policy.html` on click rather than continuing forward through the old 07→08→…→13 numeric sequence, so editing one setting doesn't accidentally walk someone through the rest. Their own forward/back page-nav arrows are deliberately left pointing along the old sequence (still driven by the shared `NAV_SEQUENCE`/`seqResolve()` skip-logic on the four optional pages among them — 09, 11, 12, 13 — which transparently skips whichever is switched off on the Optional Features hub) as a separate, manual "browse the other orphaned pages" affordance distinct from the primary Save & continue action. Its state lives under `project.floorsense.wizard` in the same `configurationProject` localStorage key described below — `setupPath`, `reservationTypes`, `checkinMethods`, `deskUserGroups`, `prebookingAdvance`, `businessHours`, `defaultReservationTimes`, `checkinWindow`, `idleRelease`, `reservationLength`, `nsnp`, `fme` and `antiDeskHogging` respectively; the Optional Features hub (module 06) introduces no state object of its own — its four switches read and write those same existing `idleRelease.enabled`/`nsnp.mode`/`fme.mode`/`antiDeskHogging.mode` fields directly, only recording its own `moduleStatus` entry for the progress bar.

The Optional Features hub's Auto-Release on Idle row later gained its own inline hours field (`#idleHoursField`, a small number input shown once that row's switch is on), so someone can set the auto-release duration directly from the hub rather than needing to open `floorsense-idle-release-09.html`. It reads/writes the same `idleRelease.idleHours` field that page's own drum uses, but defaults to 0.5 hours (30 minutes) here rather than that page's 3-hour default, since the hub is meant to offer a fast minimal setting. Separately, the Configuration Summary's Additional Options group was found to be missing an Auto-Release on Idle row entirely (it only listed Maximum desks per user, NSNP, Sit-stand desks, Recurring bookings, and Privacy) — a new "Auto-Release on Idle" row was added directly above NSNP, describing it the same way NSNP is described (off by default, configured separately). That group's single Edit link was first fixed from a stale `floorsense-reservation-length-10.html` target to `floorsense-optional-features-06.html`, then — per a follow-up request — removed entirely in favour of three individual `.row-edit-link` pills, one each on the Auto-Release on Idle, NSNP, and Sit-stand desks rows, pointing at their own dedicated pages (`floorsense-idle-release-09.html`, `floorsense-nsnp-11.html`, and `floorsense-fme-12.html` respectively) — the same "different rows live on different pages" reasoning already used for Prebooking & Duration's two row-level edit links. Recurring bookings and Privacy, previously static text, became real on/off toggles (`recurringEnabled`, default off; `dndEnabled`, default on) matching the fields already used on the additional-policy cards.

Setup Path (module 00) no longer offers a Relaxed/Pre-Configured/Strict/Build Your Own choice — that entire branching decision was removed once the page moved to the end of the core click-through chain (see the paragraph above and the file's own NOTE for the full history of both changes). It's now a single card-free confirmation screen: a short message confirming the core policy (desk allocation, check-in methods, desk & user groups, prebooking window, business hours, optional features) is configured and applies to everyone by default, plus a note that the Configuration Summary also lets you save the configuration as a General Policy and layer on neighbourhood-specific policies for individual Desk Groups. Its Continue button is the wizard's one remaining path into `floorsense-out-of-box-policy.html`, reached with no `?preset=` query string (that page already defaults to its "recommended" copy when no preset param is present). The progress-bar tooltip for this module was renamed from "Setup Path" to "Core Complete" across all 15 Floorsense pages to match; the underlying `data-module="setup-path"` key is unchanged. `floorsense-out-of-box-policy.html` itself was renamed from "Out of the Box Policy" to **Configuration Summary** in its `<title>`, hero heading, and progress-bar tooltip (filename, `data-module="out-of-box-policy"`, and its `outOfBoxPolicy` state key are unchanged — display text only).

The Configuration Summary also delivers on that "layer on neighbourhood-specific policies" note: a conditional **Additional Policies** section, hidden unless Desk Groups and/or User Groups are specifically set up to carry their own different booking policy — i.e. the "apply different policy" checkbox is ticked on `floorsense-desk-user-groups-03.html` (`project.floorsense.wizard.deskUserGroups.{deskGroups,userGroups}.policy === true`), not merely because Desk/User Groups are in use at all for grouping or reporting purposes — **and** only once the core policy above has actually been saved; the client reviews and saves the core policy first, and Additional Policies then reveals itself directly below the now-collapsed core card (rather than being visible, unsaved, at the same time). When shown, a "+ Create New Policy" button lets the client add a new named policy that starts as a clone of the *actual, currently-configured* core policy (Check-in Window, Prebooking & Duration, Check-in Behaviour, Access Methods, and Additional Options/NSNP-sit-stand-recurring-DND — read live from each of those settings' real state, not a fixed snapshot) under a custom name like "Finance" or "Help Desk," then tweak the clone's own numbers/toggles independently and Save it, up to 3 additional policies. Each clone is automatically classified as a **Desk Group** or **User Group** policy (desk if Desk Groups are enabled, otherwise user) — there's no manual toggle for this inside the card, just a read-only badge showing which it is. An info box next to the section spells out that User Group settings take precedence over Desk Group settings (e.g. a Desk Group capped at 1 desk per user is overridden by 15 for a user who's also in a User Group allowing 15) — shown only when both Desk Groups and User Groups are actually in use, since that's the only situation where the precedence rule is relevant. Each policy starts collapsed, showing its name (or an italicised "Untitled policy" placeholder) plus a one-line description ("A custom policy override for this Desk Group/User Group"), its Desk/User Group badge, a status pill, and a small X button to remove it — tapping the row (which the pill itself just reflects) expands it to reveal the actual form controls (number inputs, `.policy-switch` on/off toggles ported from the Optional Features hub, a NSNP `<select>`, and checkbox rows for Access Methods) plus its own "Save Policy" button, which collapses the card and marks it saved; editing a field again after that flips it back to unsaved until saved again. The status pill reads "Saved" once actually saved, or "Collapse"/"Expand" depending on whether the card is currently open — since tapping the header bar only ever toggles expand/collapse (saving itself happens via the dedicated button inside the expanded card), not a generic "Save" label that implied tapping the bar would save it. Trying to collapse a card while it's unsaved is itself guarded: a brand-new policy that's never been saved prompts a confirmation and is removed entirely if confirmed (autosave already persists its in-progress edits, so leaving it collapsed-but-unsaved would just be an orphaned draft); a previously-saved policy with unsaved edits instead prompts to discard those edits and reverts every field back to its last-saved values, rather than deleting a policy that already has a real, confirmed version. Collapsing an already-saved, untouched card is unaffected — no prompt, just a normal collapse. A Desk Group policy card only appears while page 03's own "apply different policy...to different desk groups" checkbox is ticked, and a User Group policy card only while its own "apply different override policy for different User Groups" checkbox is ticked — unticking one just hides that type's cards (nothing is deleted), and the 3-policy cap/count always reflects every stored policy, not just the currently visible ones, so toggling a checkbox off and on can't be used to sneak past the limit. The name field is marked required (a "Policy name*" label plus `required`/`aria-required`) and an unnamed policy can't be saved — clicking "Save Policy" while the name field is empty blocks the save, keeps the card open, and flags the name field with an inline error until a name is entered. Saving also requires at least one setting to actually differ from the core policy as it's currently configured — a named policy whose settings are all still identical to the (live) core policy is blocked from saving too, with an inline hint explaining it needs a genuine difference to count as a distinct policy; the hint clears as soon as a setting is changed and re-checks on every Save Policy click, so changing a value and then changing it back before saving still gets caught. A newly created policy opens expanded automatically, while ones loaded from a saved project start collapsed. Policy cards display saved (collapsed) policies before unsaved (still-being-edited) ones, and within each of those two groups Desk Group policies before User Group policies — a stable sort for display only, echoing the precedence notice's own Desk-then-User framing; the underlying storage order, editing, and removal are unaffected, and saving a policy simply moves it up into the saved group on the next render. Once at least one additional policy exists, the core policy column above shrinks to a denser, secondary-looking layout (reverting the moment the last one is removed), since focus has shifted to the named policies. The whole Review section is a single stacked column — core policy first, Additional Policies directly below it once revealed — rather than a side-by-side layout; the core policy column is re-centred as a single block when neither Desk nor User Groups is in use, since Additional Policies can never apply in that case. Everything autosaves on every change like the rest of the wizard.

The core policy itself is now a single collapsible card rather than six separately-boxed groups: a header bar ("Core Policy" plus a short description of what it covers, and a "Not yet saved"/"Saved" status pill) is always visible and can be tapped at any time to expand or collapse the card, and a "Save Core Policy" button at the very bottom of the expanded card marks it saved and collapses it in one action. That description stays visible (just at a smaller size) even in the denser "compact" view used once Additional Policies exist, rather than disappearing right when the card is most likely to be sitting collapsed and saved. State (`project.floorsense.wizard.corePolicyCard = { saved, collapsed }`) persists independently of the page's own "Confirm & finish" action, so the card reopens or stays tucked away exactly as it was left on a later visit. A styling audit against modules 01-04 confirmed the shared tokens (root variables, brand header, progress bar, hero/eyebrow, card border/radius conventions, action bar, page-nav, footer) already matched exactly; a handful of round-number sizes introduced on this page specifically (the Core Policy header's padding/title/description/status-pill sizing, the guides-submitted callout heading, and the disabled-button opacity) were brought back in line with the wizard's established fractional type scale and sizing conventions.

Every policy card — core, and each additional Desk Group / User Group policy — also carries a **Maximum Desks Per User** fill-in field (default 1), the same figure already referenced in the precedence-notice example above ("...allows 1 desk per user but a User Group...allows 15"). It's a plain number input, editable up to 20, autosaving independently of "Confirm & finish": on the core card it lives at `project.floorsense.wizard.outOfBoxPolicy.maxDesksPerUser`, and on each additional policy it's part of that policy's own object in `project.floorsense.wizard.additionalPolicies`. State lives at `project.floorsense.wizard.additionalPolicies` — a top-level array of up to 3 objects (each with its own `groupType: 'desk' | 'user'`), independent of the core policy's own (still-hardcoded, non-dynamic) summary text. This is purely additive to the Configuration Summary; it isn't wired into "Confirm & finish," the end-user PDF guide, or any other page's Edit links yet.

`assets/documents/floorsense-desk-booking-guide.pdf` — the end-user guide linked from the Configuration Summary's "Explain this policy to your end users" download card — was updated to add a "One desk at a time, by default" item to its Booking & Check-in section, describing the new Maximum Desks Per User setting in plain English (without getting into the Desk Group/User Group precedence mechanics, which aren't end-user-relevant). Its buildable HTML/CSS source, which hadn't previously been committed anywhere in the repo (only the compiled PDF was tracked, so this update required reconstructing the source from the rendered PDF's text and a rendered-page screenshot), is now saved at `assets/documents/src/floorsense-desk-booking-guide.html` so future content changes don't require that reconstruction again. It's rendered to PDF with [WeasyPrint](https://weasyprint.org/) (`weasyprint floorsense-desk-booking-guide.html floorsense-desk-booking-guide.pdf`, or `python3 -m weasyprint ...` if the `weasyprint` command isn't on PATH) — using CSS `@page` margin boxes (`@bottom-left`/`@bottom-right` with `counter(page)`/`counter(pages)`) for the repeating footer rather than a fixed-position element, and inline SVG icons with `stroke="currentColor"` plus a CSS `color:` rule on the containing element (not `stroke:` directly), per the same WeasyPrint quirk noted before — icons render blank otherwise. A literal `·` character is used in the footer's `content:` string rather than a `\00B7` CSS escape, since a CSS hex escape shorter than 6 digits consumes one trailing whitespace character as its terminator, silently swallowing the space that was meant to follow it.

The core policy's Check-in Behaviour group no longer has an Edit link — it never had dedicated fields to edit anyway — and instead has its own two on/off toggles, on by default: "Second swipe checks out" and "Auto-cancel when checking in elsewhere" (`swipeOutRequired`/`autoCancelOnElsewhere`, matching the field names already used on the additional-policy cards). Both autosave to `project.floorsense.wizard.outOfBoxPolicy` independently of "Confirm & finish".

"Confirm & finish" on the Configuration Summary was renamed **"Save & Email Me Summary"** and no longer just shows link buttons or auto-redirects: it still saves `outOfBoxPolicy`/`floorsense.configured`/`moduleStatus` exactly as before, then opens the client's own email app (via a `mailto:` link addressed to "Your Email" from Project Registration) pre-filled with a plain-text summary of the core policy, the **End User Guides** and **Admin Portal Guide** links, and a note that the end-user guide needs opening, printing/saving as a PDF, and attaching manually (mailto links can't carry attachments). The plain-text summary is generated by walking the core policy card's own rendered rows, so it always matches whatever's on screen — including any Check-in Behaviour toggle or Maximum Desks Per User value changed before saving — rather than being a separately hand-maintained copy. A confirmation panel names the actual recipient (or explains that "Your Email" was never filled in) and offers a manual "Continue to Project Home" link, same as before.

The Configuration Summary's "Explain this policy to your end users" download card no longer links straight to the static `assets/documents/floorsense-desk-booking-guide.pdf`. That file has no generation pipeline — it's a one-time hand-authored HTML file rendered to PDF via WeasyPrint and committed as a binary asset — so it couldn't reflect what a given client actually configured in the wizard. The card now opens `pages/floorsense-desk-booking-guide-live.html`, a live JS-populated twin of the same design (same hero/rows/CSS, including the original's `@page` print rules) that reads `project.floorsense.wizard.*` from the shared `configurationProject` localStorage key on load and fills in: the check-in window and its worked example (`checkinWindow`), how many days ahead bookings can be made (`prebookingAdvance`), how long a booking lasts (`reservationLength`, including its free-text description when the "fixed period" mode is used), how many desks a user can hold at once (`maxDesksPerUser`, including the meeting-space-tag note), which check-in methods are actually enabled (`checkinMethods`, built into a plain-language sentence rather than a fixed list), and, shown only when actually turned on, a new "Some desks power off until you check in" row for NSNP (`nsnp` — deliberately left out of the original static guide as "not end-user-relevant" back when it was a vague policy toggle, but genuinely relevant now that it's a concrete relay-driven behaviour) and a "Save your ideal sit-stand height" row for FME (`fme`). Recurring bookings and Do Not Disturb rows show or hide based on `outOfBoxPolicy.recurringEnabled`/`dndEnabled`, and the "Not switched on yet" box is rebuilt from whichever of sit-stand/recurring/DND are off, plus a static "Team bookings, booking on behalf of a colleague, and custom notifications" line with no wizard module behind it yet. A small on-screen toolbar (hidden via `@media print`) has a "Print / Save as PDF" button that calls `window.print()` — the visitor's own browser print dialog produces the PDF using this page's print CSS, so there's no client-side PDF-generation library to maintain. Auto-Release on Idle was deliberately left off this page since its effect is already covered by the check-in-window row from an end-user's point of view. The static PDF and its HTML source under `assets/documents/` are left in place but are no longer linked from anywhere in the wizard.

`smartalock-configuration-summary-08.html` (the Smartalock branch's own, read-only Configuration Summary) got the same treatment. This page previously had no completion action at all — just Print and Download JSON — so it gained a new **"Save & Email Me Summary"** primary button (Download JSON was restyled to a ghost button so there's one clear primary action). Clicking it marks `project.smartalock.configured = true`, saves `moduleStatus.summary = true` (which also marks this page's own progress-bar segment as saved — nothing previously did), builds the same kind of plain-text summary (from this page's own `.summary-group`/`.summary-row` content, all plain label/value pairs here — no toggles or number inputs), and opens a `mailto:` link with that summary plus the same End User Guides link and the Smartalock-specific Admin Portal Guide link ("SMARTALOCK FULL ADMINISTRATION GUIDE" on Notion).

This page later gained the same end-user-guide download card the Floorsense summary already had, plus lost the Download JSON button entirely (per an explicit request — Print is now the only `.ghost` button alongside "Save & Email Me Summary"). The new `pages/smartalock-locker-guide-live.html` is the Smartalock branch's first end-user guide of any kind — there was never a static Smartalock PDF the way `assets/documents/floorsense-desk-booking-guide.pdf` existed for Floorsense — built the same way as `floorsense-desk-booking-guide-live.html`: same hero/rows/footer design (recoloured to this app's Smartalock blue instead of Floorsense green), a "Print / Save as PDF" toolbar button, and dynamic content read from `project.smartalock.wizard.*` on load. It covers: how a locker is obtained (`reservationType.reservationTypes` — admin-assigned, self-reserved with a duration note, and/or parcel delivery, combined into one sentence when more than one applies), how the door opens (`lockerBehaviour.lockerBehaviour`/`pushOpenScope` — Pop Open vs. Push to Open, describing a "specific" scope only as "certain lockers" rather than naming the actual bank/numbers), which access methods are available (`accessMethods.selected`, built into a plain-language list the same way the Floorsense guide lists check-in methods), locker policy (`locker.lockerLimit`, `locker.releaseBehaviour`, and an idle-release row shown only when `locker.idleDuration` is actually set), which kiosk actions are available (`kioskCustomisation.{openEnabled,lockerEnabled,qrEnabled,cardEnabled}`, with a "not available at this kiosk" box listing whichever are off), and which locker types the site offers (`lockerType.selected`/`exampleNumbers`). The download card on the summary page and the Save & Email mailto body's "isn't attached automatically" note both mirror the Floorsense page's own wording verbatim.

Desk Groups (Neighbourhoods) & User Groups (module 03) — originally inserted between Check-in Methods and Setup Path, and now sitting between Check-in Methods (02) and Prebooking (04) in click-through order since Setup Path moved to the end of the core chain — was, at the time it was added, the newest addition to the main flow (not one of the optional tail-end modules). It covers two independent topics with the same shape: a multi-select checkbox grid (`.group-check-card`, ported from Check-in Methods' `.desk-check-card`) — "not use" (each grid's first option, tagged **Recommended**), "provide a list/floorplan (or spreadsheet, for User Groups)", and "apply different override policy" — where "not use" is mutually exclusive with the other two but those two can combine freely; and a conditional policy textarea that only appears once the "apply different policy" option is ticked. Desk Group Setup defaults to "not use" (no concrete example was supplied for it); User Group Setup defaults to "provide" + "policy" both checked, since the brief supplied a real example override policy ("Only Client Care can book desks in the Client Care area; Only HR can book desks in the HR area"), prefilled into that field. An amber caution notice (ported from Setup Path's `.setup-notice`) originally repeated at the bottom of each column warning that policy overrides complicate setup and maintenance; it was later consolidated into a single notice shown once at the top of the page, and reworded again into plainer, client-facing language once the admin-facing phrasing proved unclear: "You don't need to set up Desk Groups unless you want different booking rules for a specific area. Likewise, extra User Groups are optional — only add them if your policy really needs different rules for different groups of users, as each one adds a bit more setup complexity."

Prebooking (module 03) and Business Hours (module 04) swapped numbers per a later reorder request, so Prebooking now immediately follows Check-in Methods/Setup Path and Business Hours comes right after it. Business Hours is a single-topic page in the same one-card, one-timeline explainer style as Check-in Window: one card with a live diagram driven by a time drum on either side (Opens / Closes), setting the standard business hours used as a default for most users. Default Reservation Times (module 07, formerly 05) and Check-in Window (module 08, formerly 06) were originally one combined page ("Check-in Policy") hosting two numbered sections; they were later split into their own single-topic pages, each built as a single explainer card: an icon + description, a live diagram, and a footer strip with supporting context. Default Reservation Times comes right after Business Hours (and, since the Optional Features hub was inserted, right after that hub too) so its default start time is already saved by the time a user reaches Check-in Window, whose own worked example depends on it. Auto-Release on Idle (module 09, formerly 07) uses the same card pattern but as its own single-topic page too, since it was originally going to be a third numbered section on the combined page before being split out — its card and diagram were later restyled to match Check-in Window's/Default Reservation Times' Apple Clock time-drum look (a single duration drum driving a fixed "Reserved" pin and an enlarged "Released" pin), replacing an earlier static SVG flowchart and inline number field.

NSNP (module 11, formerly 10), appended after Reservation Length, was the wizard's first genuinely optional module: "No Swipe No Power" keeps a desk's outlets powered off until someone checks in with a valid badge swipe, then off again once their reservation ends (subject to the grace period below); permanently assigned desks are the one exception and stay powered on all the time. It requires NSNP relay units installed at each desk to function. Every piece of copy on the page — hero sub, main description, mode-card descriptions, and the "Other" placeholder — was later reviewed and rewritten to consistently reflect this off-by-default/permanently-assigned-exception logic, replacing an earlier framing centered on "occupied without a valid swipe" that didn't mention permanently assigned desks. ### Conventions used across the 10 wizard pages

- **Shell markup**: `.page-main` > `.panel-topbar` (`.top-frame` with `.brand` + horizontal `.progress-bar`) + `.panel-intro` (hero title/subtext) → `.panel-scroll` (the actual form content) → `.action-bar` (Reset / Save & continue).
- **Progress bar**: `.progress-seg` per module; `.saved` = previously completed, `.current` = active page, hover shows a tooltip with the module name.
- **Typography**: Inter throughout. Hero titles are 76px/weight 200, forced onto a single line via `white-space: nowrap` + a `width:100vw; left:50%; transform:translateX(-50%)` breakout so long titles don't get clipped by their column.
- **State**: each page reads/writes a single `localStorage` key, `configurationProject`, shaped roughly as:
  ```
  {
    id, created, updated,
    registration: { customer, site, projectName, contact, email, phone, ... },
    smartalock: {
      configured, templates,
      wizard: {
        moduleStatus: { registration: true, it: true, ... },  // drives the progress bar
        it: {...}, accessMethods: { selected: [...], cardAssignMethod, pinAssignMethod }, ...
      }
    },
    floorsense: { configured, templates, wizard: {} }
  }
  ```
  Each page's own section of `wizard` is independent — check the `<script>` block at the bottom of any page for its exact fields.
- **Images/diagrams**: pages with a right-hand visual panel (e.g. IT Configuration's architecture diagram) swap the `<img src>` via JS based on form selections — see `ARCH_VISUAL` in `smartalock-it-configuration-02.html` for the pattern.
